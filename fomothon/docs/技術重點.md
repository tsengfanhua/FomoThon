# 技術重點

整理日期：2026-11-12｜供簡報與說明使用。所有數字都可以用文末的指令重跑。

Fomo鬆的技術重點有三項：**用 MCP 把媒合 Agent 開放給任何 AI 助理**、**依任務分流到不同模型，並以檢核決定是否升級**、**用資料品質規則與標準答案管住資料**。三項共用同一個原則：模型與外部資料都視為不可信，結論必須通過可重現的檢核。

## 1. MCP：把三個媒合 Agent 變成任何 AI 助理都能用的工具

### 1.1 為什麼做

學生不一定會打開我們的網頁，但會用 Claude、ChatGPT 或 IDE 裡的 AI 助理。Model Context Protocol（MCP）是 AI 助理呼叫外部工具的開放標準。把 Agent 做成 MCP 伺服器，任何支援 MCP 的用戶端都能直接使用共用 Skill 資料庫與三個媒合 Agent，學校其他單位的系統也能用同一個介面接進來。

### 1.2 做了什麼

| 項目 | 內容 |
| --- | --- |
| 協定層 | 自行實作 JSON-RPC 2.0 與 MCP 生命週期（零相依），支援 2025-11-25、2025-06-18、2025-03-26、2024-11-05 四個協定版本 |
| 傳輸 | stdio（Claude Desktop、Claude Code、MCP Inspector）與 Streamable HTTP（遠端用戶端） |
| 工具 | 11 個唯讀工具：技能搜尋與詳細資料、本人能力檔案、競賽清單／推薦／分析、找隊友、找指導老師、課綱技能萃取、任務辨識與規劃、資料品質檢核 |
| 資源與提示範本 | 5 個資源＋2 個資源樣板（技能、課綱）；2 個提示範本（參賽準備、能力缺口學習計畫） |
| 結構化輸出 | 每個工具都宣告 `outputSchema`，回傳 `structuredContent`；伺服器回傳前先自我驗證 |
| 可追溯 | 工具內部的 Agent 決策與工具調用放在結果的 `_meta["fomothon/trace"]`；每次呼叫寫入稽核 |

### 1.3 安全設計

- **唯讀**：送出邀請不開放給外部 AI，仍由學生在系統內確認（人工確認的原則不因為換了用戶端而失效）。
- **身分綁定**：stdio 一個程序一個帳號；HTTP 每把個人權杖一個帳號（只存雜湊、有期限、可撤銷），連線階段綁定權杖。
- **資料最小化**：輸出不含成績與精確分數；自動化測試逐一檢查輸出欄位。
- **外部文件標示**：以 MCP 提供課綱時，內容已去除標籤，並標示 `untrusted_external_document`，提醒用戶端模型「這是資料，不是指令」。
- **HTTP 端點**：預設關閉；檢查 Origin 與 Host（防 DNS rebinding）、速率限制、請求大小上限。

### 1.4 怎麼證明它是「真的 MCP」

自己實作協定層的風險是「自以為相容」。所以另外用官方工具驗證：

| 驗證 | 結果 |
| --- | --- |
| 官方 MCP TypeScript SDK 1.32.2 的 client，以 stdio 連線 | 11 個工具全部呼叫成功；SDK 依每個工具的 outputSchema 驗證 structuredContent，全部通過 |
| 同一個 client，以 Streamable HTTP＋Bearer 權杖連線 | 通過（取得 Mcp-Session-Id、呼叫全部工具、結束連線階段） |
| MCP Inspector CLI 2.15.0 | stdio 與 Streamable HTTP（帶權杖）都能列出 11 個工具並呼叫工具；不帶權杖時被拒絕 |
| Claude Code | 讀到專案附的 `.mcp.json` |
| 自己的測試 | 18 項：版本協商、生命週期、錯誤分類、輸出自我驗證、隱私、權杖與連線階段 |

## 2. 多模型：依任務分流，未通過檢核才升級

### 2.1 為什麼做

不同任務需要的能力差很多：任務辨識是 6 選 1 的分類，小模型就夠；課綱萃取要讀懂語意，需要較強的模型。全部用最強的模型成本高、延遲長；全部用小模型品質不穩。另一個考量是個資：學校可能希望部分資料不離開校園。

### 2.2 做法

1. **路由表**（`config/models.json`）：6 個端點（Claude Opus／Sonnet／Haiku 5.5、OpenAI 相容、Gemini 相容、校內地端模型）與 6 組路由。例如 `claude-tiered`：任務辨識用 Haiku 5.5，萃取與說明用 Sonnet 5.5。
2. **以檢核決定升級**：每個用途是一條模型鏈。前一個模型呼叫失敗，或輸出**未通過系統原本的檢核**（例如萃取的出處不是課綱原文、說明出現事實以外的數字），就改用下一個模型；全部失敗才退回規則。所以「先用便宜的模型」不會降低正確性的底線。
3. **資料保護在路由器統一處理**：送往雲端端點的內容自動遮蔽 Email、電話、身分證字號、學號；建議說明中的人名換成代號，回到本機才換回並做事實檢核。地端端點不離開校園，送原文。
4. **各家 API 的差異**：Anthropic 用官方 SDK 的結構化輸出；Opus 與 Sonnet 5.5 啟用伺服器端拒答備援，Haiku 5.5 不支援就不帶這個參數。OpenAI 相容端點（含 Ollama、vLLM、Gemini 相容端點）用 JSON 模式，回來一律在本機驗證。

執行紀錄會寫出每次升級，例如：

```text
LLM（intent）完成：claude-haiku-5-5（未通過檢核） → claude-sonnet-5-5 通過
```

### 2.3 評比方法

`eval/models.js` 不另外編題目，而是**錄下系統實際送出的請求**再重播：

1. 以「錄音模式」跑一遍系統：18 句任務辨識、24 門課綱萃取、19 個情境的協調器決策與說明，共 73 個請求，每個都帶著系統原本的檢核函式。
2. 把同一批請求送給每個模型（或每組路由），用同一套檢核計分。
3. 指標：任務辨識正確率、萃取 F1、萃取幻覺率（提出但被檢核丟棄的比例）、下一步合法率、說明通過事實檢核的比例、延遲 p50／p95、成本。

**目前狀態**：路由、升級、遮蔽、代號化與評比工具都已用模擬伺服器與假模型測過，**還沒有對真實模型執行**，所以沒有各模型的比較數字。執行一次的規模是 73 個請求，費用依模型而定，需要團隊決定是否使用金鑰執行。

## 3. 資料品質：資料契約、23 條規則與標準答案

### 3.1 為什麼做

媒合結果的好壞，取決於 Skill 資料庫、課綱與證據的品質。別名寫錯一個，整批學生的能力就會被誤判；課綱被塞了指令，推估就可能被帶偏。資料品質必須能量測、能擋下壞資料。

### 3.2 三道關卡

| 關卡 | 時機 | 做法 |
| --- | --- | --- |
| 資料契約 | 建庫前 | 每類資料一份 JSON Schema（`data/schemas/seed-entities.json`） |
| 品質閘門 | 建庫前、`npm run dq` | 23 條規則、6 個面向；有 error 等級問題就拒絕建庫 |
| 課綱品質評估 | 每次盤點 | 週數、教學目標、評量權重、可疑內容（在去除標籤前檢查）；不合格的課綱推得的技能降為「推估」 |
| 資料版本 | 啟動時 | 舊版資料庫的證據沒有品質評估時，自動重新盤點一次 |

### 3.3 結果

- 總分 **99.1／100**，閘門通過。仍有 4 條 warning，其中 3 條是刻意放入的攻擊測試資料，1 條是待補的外部標準對應（Git）。
- **規則抓到的真實錯誤**：JavaScript 的別名「JS」會誤中「Node.js」「Vue.js」，讓後端課程被誤判成教 JavaScript。已修正並加上回歸測試。這也是資料品質規則的價值：它不是事後的分數，而是會找出系統錯誤的檢查。
- **供需分析**：報告列出每項競賽需要的技能有幾門課在教，供給少的技能（例如 UI 介面設計 3 項競賽需要、2 門課在教）可以回饋給系所。

### 3.4 課綱萃取的標準答案

| 步驟 | 做法 |
| --- | --- |
| 標註 | 兩位彼此獨立的 AI 標註者（不同模型、不共享脈絡、看不到萃取規則與結果）各自標註 24 門課綱 |
| 一致性 | Cohen's κ = **0.944**（1,104 個課程 × 技能組合；兩人皆標 63 項，只有一人標 7 項） |
| 標準答案 | 兩人都標的 63 項為正例；分歧的 7 項列為模糊項、不計分，避免由知道萃取結果的人裁決 |
| 規則萃取 | Precision **74.4%**、Recall **92.1%**、F1 **82.3%** |
| 誤判類型 | 程式語言只當工具使用（機器學習課的 Python）、複合詞（「演算法偏誤」誤中「演算法」） |

這組數字的用途是「當基準」：LLM 萃取與規則＋LLM 合併能不能提高 Precision，用同一份標準答案就能比較。限制是標註者為 AI，正式評測前要請兩位教師複核，再用同一支程式重算。

## 4. 與 Agent 評測的關係

| 層次 | 驗證內容 | 結果 |
| --- | --- | --- |
| 任務層 | 27 個案例（任務完成、重新規劃、失敗處理、安全）＋固定工作流基準 | 27/27；基準 12/19 |
| 模型層 | 同一批真實請求 × 各模型 | 工具完成，待執行 |
| 資料層 | 23 條資料品質規則；萃取標準答案 | 99.1／100；F1 82.3%（κ = 0.944） |
| 介面層 | 官方 MCP SDK 互通 | 11 個工具全部通過 |
| 程式層 | 105 項自動化測試 | 全部通過（安裝 SDK 時），行覆蓋率 96.5% |

## 5. 重跑方式

```bash
npm test                                 # 105 項測試（互通測試需先 npm install）
npm run eval                             # Agent 評測 → eval/results/REPORT.md
npm run dq                               # 資料品質 → data/quality/REPORT.md
node eval/extraction.js                  # 萃取準確度 → eval/results/EXTRACTION.md
node eval/models.js --dry-run            # 多模型評比：錄製請求
node eval/models.js --profiles claude-tiered,claude   # 實際評比（需要金鑰、會產生費用）
npx @modelcontextprotocol/inspector --cli node src/mcp/stdio.js --method tools/list
```

## 6. 獨立審查

程式完成後請一位不帶開發者結論的審查者逐項找反例（每項都附重現步驟）。第二次審查針對 MCP、多模型與資料品質：0 項重大、1 項高（超長陣列參數可拖慢伺服器）、9 項中（例如連線階段可被別的權杖擠掉、stdio 遇到 U+2028 會切斷訊息、部分電話與證號格式沒被遮蔽、資安課程的主題詞被誤判為可疑內容）、8 組低。全部已修正，並有 18 項回歸測試（`test/review2.test.js`）。明細見 `docs/資料與安全自評表.md` 第 7 節。

## 7. 答詢時要誠實說明的地方

- 多模型評比還沒有真實模型的數字；目前所有 LLM 相關的品質數字只有規則基準。
- 萃取的標準答案是 AI 預標註，還沒有教師複核。
- MCP 的 HTTP 驗證是個人權杖，不是規範建議的 OAuth 2.1；要讓雲端 AI 平台直接連線，還要補 OAuth 與 HTTPS。
- MCP 協定層與 JSON Schema 驗證器只實作本專案需要的子集。
- 資料都是合成的；資料品質分數反映的是這份合成資料，不是真實校務資料。
